# Architecture

The project is a local Python patient simulator built with LiveKit Agents. One process creates an `AgentSession`, places a call through the configured LiveKit outbound SIP trunk, and runs a cascaded speech pipeline: Deepgram Nova-3 turns the assessment agent's speech into text, GPT-4.1 mini chooses the simulated patient's next response, and Cartesia Sonic-3 speaks it. All three stages use LiveKit Inference and the LiveKit project credentials. LiveKit turn detection, dynamic endpointing, and adaptive interruption handling coordinate when the patient responds. This keeps the challenge-required speech-to-text, text-LLM, and text-to-speech stages separate and avoids another live provider key. The `openai/gpt-4.1-mini` value is a LiveKit Inference model identifier. A temporary direct OpenAI voice pipeline was tried and reverted after the user found it slower and less natural; calls 027–030 preserve that experiment as historical evidence. No per-stage latency measurement was collected, so the cause of the reported delay is not established. The fixed assessment destination and caller-number checks help prevent accidental calls to another number.

During a call, a receive-only recorder subscribes to the patient and assessment-agent audio tracks and writes a stereo recording locally, with each speaker on a separate channel. After the call, the application exports the live transcript, validates and fingerprints the recording, then runs rule-based checks, scenario assertions, and optional semantic review. Runtime evidence is saved under `artifacts/calls/<call>/` as audio, transcript, metadata, timeline, and evaluation files; the curated submission copy is numbered under `artifacts/submission_calls/`. Reviewers should listen before treating transcript timing or wording as definitive. `OPENAI_API_KEY` is optional for post-call transcription or semantic judging only; without it, the live transcript and local evaluation remain available. Local files keep setup simple and avoid S3, a separate recording service, and another worker process. Since recordings and transcripts can contain identifiable voice and test details, any shared repository containing them must remain private and access should be limited to the intended reviewer.
