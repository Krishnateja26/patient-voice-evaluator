# Architecture

I built the caller in Python with LiveKit Agents. A single local command starts an AgentSession and calls the fixed assessment number through a LiveKit outbound SIP trunk. For the patient side, I use three separate LiveKit Inference stages: Deepgram Nova-3 transcribes the receptionist's speech, GPT-4.1 mini chooses the patient's next response, and Cartesia Sonic-3 speaks it. LiveKit's turn detection, dynamic endpointing, and adaptive interruption handling help the patient wait, respond, or barge in naturally. The model identifier `openai/gpt-4.1-mini` is routed through LiveKit Inference; the live caller does not use my direct OpenAI API key. I use my existing Twilio number through a Twilio Elastic SIP trunk connected to LiveKit, so Twilio carries the telephone call while LiveKit runs the agent session. I tried a direct OpenAI speech pipeline for calls 027–030, then returned to the LiveKit setup after I found the caller less natural and slower. I did not capture comparable per-stage measurements during that trial, so the exact source and size of the delay are not proven.

I record the patient and receptionist on separate channels in one local MP3. After each call, the application saves transcripts, metadata, hashes, a session timeline, timing summaries, and an automatic evaluation in the call folder. I selected and renumbered 18 call folders for the private GitHub repository; each retains a link to its original call ID and scenario. The automatic checks help me find exchanges worth reviewing, but they do not replace listening: I treat a spoken claim as evidence of what the receptionist said, not proof that a booking, ticket, or staff notification happened in a backend system. An optional OpenAI key is used only for post-call transcription or semantic judging. Local recording keeps the setup simple and avoids S3 or a separate recording worker. Because the audio and metadata contain test identity details, I keep the repository private.
